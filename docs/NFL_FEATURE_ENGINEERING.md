# NFL Feature Engineering

This describes the feature engineering built for NFL — what it computes, where it runs, and what it makes it possible to predict

## Feature Logic

The math itself lives in `Source/library/features/nfl.py`, deliberately *not* inside `feature-engineering/nfl/`. The reason: the same functions are called from two places — here, in bulk, to build a training set, and by the inference Lambda's `live_features.py` (`Source/aws-lambdas/nfl/predict/`, see "Serving layer" in `design/DATA_SCHEMA.md`), computing a live feature vector for one upcoming game. Keeping one shared implementation instead of two copies is what prevents train/serve skew (the model being trained on features computed slightly differently than what it's fed at prediction time). The one thing that differs between the two callers is how history gets gathered, not the feature math itself: batch feature engineering loads the whole table once and walks it incrementally; live inference looks up exactly one event's worth of context via `FeatureStorage`'s one-team/one-player/one-event methods, since it's only ever building a single row per request.

### Event-level features (`build_event_features`)

One row per completed game. Inputs to the model:

| Feature | What it captures |
|---|---|
| `week` / `season_type` | How far into the season the game falls, and whether it's regular season or postseason. Both already land in DynamoDB via `scoreboard_event_to_event_item` (`library/normalize/espn.py`) — no new data source, they just weren't being surfaced as model inputs before |
| `home_elo` / `away_elo` / `elo_diff` | Each team's Elo-style rating going into the game (see below) |
| `home_rest_days` / `away_rest_days` | Days since each team's previous game |
| `home_avg_points_scored` / `home_avg_points_allowed` (and the away equivalents) | Rolling average over the last 5 games (configurable via `ROLLING_WINDOW`) |
| `home_games_played` / `away_games_played` | How much history backs those averages — lets a model learn to trust an early-season row less |
| `venue_indoor` | Whether the game was played in a dome — weather is meaningless for an indoor game, so this lets the model treat `weather_temperature` differently (or ignore it) for those rows |
| `weather_temperature` | Game-time temperature from ESPN's venue data. Frequently `null` — most reliably for indoor games, where it doesn't apply, but also for some outdoor games ESPN simply didn't report on. A partial signal, not a guaranteed one |
| `home_qb_avg_passing_yards` / `home_qb_avg_passing_tds` / `home_qb_avg_interceptions` (and the away equivalents) | Rolling average over each side's **starting QB's own last 5 games** — not the team's, so a backup filling in doesn't inherit the usual starter's numbers, and a traded QB's history follows them rather than resetting |
| `home_qb_games_played` / `away_qb_games_played` | How much of that QB's own history backs the averages above; `0` when a starter couldn't be identified for that game |
| `home_rb_avg_rushing_yards` / `home_rb_avg_rushing_tds` (and the away equivalents) | Same rolling-history approach as the QB fields, tracking each side's identified lead rusher |
| `home_rb_games_played` / `away_rb_games_played` | How much of that rusher's own history backs the averages above |
| `home_wr_avg_receiving_yards` / `home_wr_avg_receiving_tds` / `home_wr_avg_receptions` (and the away equivalents) | Same rolling-history approach, tracking each side's identified lead receiver |
| `home_wr_games_played` / `away_wr_games_played` | How much of that receiver's own history backs the averages above |
| `home_avg_turnovers` / `home_avg_total_yards` / `home_avg_possession_time_seconds` (and the away equivalents) | Rolling average of each team's own box score totals (see `team_game_stats` in `design/DATA_SCHEMA.md`) |
| `home_avg_penalties` / `home_avg_penalty_yards` (and the away equivalents) | Rolling average of each team's own penalty count/yardage — same `team_game_stats` box score source and rolling mechanism as turnovers/total yards above. `stat_line` has carried `penalties`/`penalty_yards` since normalize.py's `totalPenaltiesYards` split existed, for the entire historical backfill; this was simply never read into the feature vector before |
| `home_third_down_pct` / `home_red_zone_pct` (and the away equivalents) | Conversions over attempts across the rolling window (not an average of per-game percentages, which would let a small-sample game skew the rate) |
| `home_box_games_played` / `away_box_games_played` | How much team box score history backs the averages above |
| `is_divisional_game` | Whether both teams are in the same division (`library/features/nfl_teams.py`) — divisional matchups are played more often and behave differently in some analyses |
| `is_international_game` | Whether the game was played at one of `nfl_teams.INTERNATIONAL_VENUES` (London, Munich, etc.) rather than either team's home market |
| `home_travel_km` / `away_travel_km` | Distance each team travels to the game, computed between team home-market coordinates and, for international games, the actual host-city coordinates instead of assuming the home team traveled 0 km |
| `home_win_streak` / `away_win_streak` | Each team's current run of consecutive wins (positive) or losses (negative), reset by a tie — a short-term-momentum signal distinct from Elo's longer-run skill estimate |
| `home_coach_experience` / `home_coach_season_win_pct` (and the away equivalents) | Each team's current head coach's tenure with that team (years) and this-season win rate, both ESPN's own numbers used directly — no derivation. See "Coach, injury, and depth-chart data" below; forward-only, `null` on any event ingested before this shipped |
| `home_qb_injury_status` (and the away equivalent) | Ordinal severity (0=no report/healthy, 1=Questionable, 2=Doubtful, 3=Out) of the presumptive starting QB's current injury status, looked up by matching `home_qb_games`' identified player against the event's own `home_injuries` snapshot. `null` (not `0`) when the event has no injuries data at all — a real missing value, not a false "definitely healthy" signal |
| `home_team_injury_count` (and the away equivalent) | Count of the home team's players currently listed Doubtful or Out (Questionable isn't counted — most Questionable players play). `null` when the event has no injuries data at all |

Also carried on the row for reference, but **excluded from training** by `train_win_probability_model.py` (raw strings aren't model-consumable without encoding — see `design/DATA_SCHEMA.md`): `venue_city`, `venue_state`.

Labels carried on the same row (the training targets, not inputs): `label_home_won`, `label_home_score`, `label_away_score`.

**Elo ratings** (`compute_elo_ratings`) are computed by walking every team's games in chronological order and updating a running rating after each result, with a home-field advantage added to the expected-score calculation and a margin-of-victory multiplier (`_mov_multiplier`) scaling each update — a blowout moves ratings more than a one-score win, log-dampened and further dampened when the winner was already a big favorite. Defaults: starting rating 1500, K-factor 20, home advantage 55 rating points. Each event gets its **pre-game** rating recorded (using the post-game rating would leak that game's own outcome into its own features). Ties apply no MOV scaling (there's no winner to measure a margin from).

**Identifying a game's key players** (`identify_starting_qb` / `identify_lead_rusher` / `identify_lead_receiver`): a team's box score doesn't flag who started, so these pick whoever had the most passing attempts / rushing attempts / receiving targets in that game — correctly favoring the primary contributor over a backup with a handful of mop-up reps. `build_dataset.py`'s orchestration groups `player_game_stats` by `(event_key, team_id)`, runs each identify function per side per event, and tracks each identified player's own rolling history by `entity_id` (the same incremental, capped-at-`window` approach used for team history) rather than re-deriving it per game. A raw player identity isn't used as a feature directly — it's high-cardinality and doesn't generalize across roster turnover — so only the derived rolling stats above are surfaced. Same rule for coach identity below: `home_coach_id`/`home_coach_name` are carried on the event item for reference, never fed to a model, only the derived `home_coach_experience`/`home_coach_season_win_pct` are real features.

**Team box score stats**: ESPN's box score also reports team-level aggregates (turnovers, total yards, penalties, time of possession, third/fourth-down and red-zone efficiency) directly, separate from individual player stat lines — stored in the `team_game_stats` table and tracked with the same incremental rolling-history approach as team scoring, keyed by `team_id`.

**Coach, injury, and depth-chart data**: unlike everything above, these don't come from the same scoreboard/box-score payloads ingest already fetched — they're pulled from two other ESPN endpoints (`sports.core.api.espn.com`'s separate `$ref`-based "core" API for coaches/injuries, via the new `library/http/espn_core.py`; a real depth-chart endpoint on the same `site.api.espn.com` host everything else uses, via a new method on the existing `NFLClient`) and attached directly onto each event dict by ingest's `_enrich_events` (`aws-lambdas/nfl/ingest/handler.py`) before every scoreboard write, landing on the event item the same way `venue_indoor`/`weather_temperature` do — no new DynamoDB table. Forward-only: ESPN's coach/injury data is current-state only, with no historical-as-of-date endpoint, so every event ingested before this shipped simply has none of these fields, the same sparse-optional convention `weather_temperature` already established. Ingest now runs daily in-season (`Terraform/scheduler-nfl-ingest.tf`), not just Tue/Wed, specifically because injury reports change through the week in a way box scores and coach data don't; feature engineering (`Terraform/scheduler-nfl-feature-engineering.tf`) follows the same daily cadence, one hour after that day's ingest run, so a training run always has the freshest captured data flowing through. `scoreboard_event_to_event_item` re-derives and rewrites these fields on every cycle, so a lighter "injuries-only" mode that skipped re-fetching coach/depth-chart data would silently wipe those fields on the next rebuild — confirmed as a real bug in an earlier version of this design, which is why there's only the one enrichment path, not two.

Depth-chart data isn't a training feature at all — it's used exclusively at **live-serving time** (`aws-lambdas/nfl/predict/live_features.py`) to pick which player to build a prediction for. `_presumptive_leader_and_history`/`_team_leader_candidates` prefer the real depth chart (rank order, filtered to exclude anyone Out/Doubtful) over the training-time "whoever had the most volume last game" heuristic above, since a real depth chart correctly surfaces a genuine backup who simply hadn't played much yet — exactly the case the volume-based heuristic misses when a starter goes down. Falls back to the volume-based heuristic only when depth chart data isn't available for that team/position at all (older events, or a fetch failure); if the depth chart IS available but everyone at a position is currently hurt, that's treated as a real "no leader available" result, not a reason to fall back and risk re-selecting the very player just excluded.

**Division/travel/streak** (`library/features/nfl_teams.py`, `current_streak`): division and each team's home-market coordinates are a static, hardcoded table, not fetched from any API — the last NFL realignment was 2002, well before this project's data window, so a fixed table is simpler and more robust than depending on an ESPN endpoint for something that essentially never changes. `current_streak` walks a team's own event history backward from most recent, comparing scores directly (not each participant's `won` flag, which reads `False` for both sides on a tie) so a tie correctly resets the streak instead of counting as a loss.

`travel_distances_km` also hardcodes `INTERNATIONAL_VENUES` (London, Munich, Mexico City, etc.) so the handful of neutral-site games each season get real travel distances for both teams instead of assuming the designated home team is at their actual home market. This table needs a manual update whenever the NFL adds a new host city — `build_event_features` logs a warning (venue has no US state and isn't in `INTERNATIONAL_VENUES`) when it hits one it doesn't recognize, so a new city shows up in CloudWatch instead of silently producing wrong travel numbers for that game.

### Player-level features (`build_player_features`)

One row per player per completed game. For every stat a player's `stat_line` contains (passing yards, receptions, field goals made — whatever ESPN reports for that position), the function averages it over that player's last 5 games *that had that stat*, rather than diluting the average with games where the stat didn't apply. This is generic across positions on purpose — a QB's passing keys and a kicker's field-goal keys never collide, so there's no per-position hardcoding.

Also included: `games_played` and `starts` over the window, plus `games_with_<stat>` for every stat key the player has (how many of the windowed games actually had it, distinct from `avg_<stat>` — see `train_player_prop_model.py`'s volume filter below for why this matters). Label carried on the row: `label_stat_line` (that game's actual stat line, JSON-encoded since Parquet/Arrow needs a stable schema across rows and stat-line keys vary by position) and `label_started`.

**Event context, reoriented to one player's perspective:** the same context the win-probability model uses, but a player-prop row has no "home team" of its own, so these are framed as own/opponent rather than home/away:
- `is_home` — whether the player's own team was playing at home.
- `opponent_id` — carried for reference (a future opponent-defense-strength feature would key off this), not a feature itself; a raw entity ID isn't model-consumable any more than `venue_city` is.
- `week` / `season_type`, `venue_indoor` / `weather_temperature` — identical fields to the event-level table above, just looked up via the event the player-game belongs to.
- `rest_days` — the player's own team's days since its previous game (not the player's own days since playing, which would be the same thing barring injury absences this dataset doesn't track).
- `own_elo` / `opponent_elo` / `elo_diff` — the player's own team's Elo and the opponent's, from the same `compute_elo_ratings` output the win-probability model uses. This is the cheapest available proxy for opponent quality; a true opponent-specific defensive-stat feature (e.g. passing yards allowed) isn't built yet — `team_game_stats`' rolling averages are offense-centric (a team's own output, not what it's allowed), so that would need new aggregation logic, not just wiring an existing field.
- `is_divisional_game`, `is_international_game`, `travel_km` — same `library/features/nfl_teams.py` helpers as the win-probability model, `travel_km` resolved to whichever of `travel_distances_km`'s two return values matches the player's own team.

**Known simplification — usage rate:** what's implemented is raw per-game volume (attempts, targets, carries — as ordinary rolling-average stat_line keys), not a true usage-rate metric. A true usage-rate metric (share of team volume, e.g. target share) needs every player on the team's stat line for the same game to compute a team total, which isn't wired up yet. This is a follow-up, not something silently skipped.

## Models trained on these features

`Source/model-training/nfl/` -- one script per predicted value, sharing loading/splitting/evaluation/artifact-writing/promotion plumbing via `library/ml/training_common.py`, and the multi-algorithm tournament mechanics via `library/ml/backtest.py`, so that logic exists once regardless of which target a given script trains or which sport eventually joins NFL. Every target runs a full candidate tournament on each scheduled retrain (see `library/ml/model_types.py` for the adapter roster: XGBoost, logistic regression, random forest, and a small MLP for classification; XGBoost, ElasticNet, random forest, and MLP for regression) rather than fitting one fixed algorithm -- whichever candidate scores best on that target's gate metric gets promoted, so the production algorithm can change between retrains as more data comes in, with no code change needed.

| Predicted value | Model type(s) trained & evaluated | Features used |
|---|---|---|
| Home team win probability (`label_home_won`) | `train_win_probability_model.py` -- XGBoost, logistic regression, random forest, and MLP classifiers compete on `log_loss`; the winner is versioned under `nfl/win-probability/` | Every event-level feature in the table above |
| Game score -- margin, home score, or away score, one model per target | `train_score_model.py` -- one script, not one script per target; which target to train is set by the `SCORE_TARGET` environment variable (`margin`, `home_score`, or `away_score`) at `aws ecs run-task` time (see `Terraform/ecs-task-nfl-train-score-model.tf`), versioned independently under `nfl/score-margin/`, `nfl/home-score/`, `nfl/away-score/`. XGBoost, ElasticNet, random forest, and MLP regressors compete on `rmse`. All three labels are derived from the already-present `label_home_score`/`label_away_score` at training time -- no new feature engineering needed for any of them. Each model card's naive baseline recombines existing rolling averages the way a simple power rating would (`home_avg_points_scored` with `away_avg_points_allowed` for a home-score prediction, etc.) rather than assuming a flat 0 | The identical event-level feature set as win probability -- same dataset, same split, different label |
| Player stat props -- one model per stat (e.g. `passing_yards`, `rushing_yards`, `receiving_yards`, `defensive_sacks`) | `train_player_prop_model.py` -- one script, not one script per stat; which stat to train is set by the `TARGET_STAT` environment variable at `aws ecs run-task` time (see `Terraform/ecs-task-nfl-train-player-prop-model.tf`). Same four-regressor tournament as the score models. The dataset is filtered to rows where the player recorded `TARGET_STAT` in the game being labeled, has at least `MIN_PRIOR_GAMES_WITH_STAT` prior games with it (`games_with_<stat>`), AND has an `avg_<stat>` at least `MIN_AVG_FRACTION_OF_MEDIAN` of the remaining population's own median -- the first two filters catch a true one-off (a WR's single career pass attempt), the third catches a player who clears that bar by recurring at trivial volume instead (e.g. a real but minor wildcat passing package) rather than being a genuine participant in this stat category. Every model card also reports a naive baseline (predicting `avg_<stat>` directly, no model at all) alongside each candidate's rmse/mae, since a large input-feature-driven baseline being available makes "is this actually better than assuming recent history repeats" a real, always-answerable question rather than a one-off analysis | That player's own rolling per-stat averages (`avg_<stat>`), `games_with_<stat>`, `games_played`, `starts`, plus event context reoriented to the player's own/opponent perspective (`is_home`, `week`, `season_type`, `venue_indoor`, `weather_temperature`, `rest_days`, `own_elo`/`opponent_elo`/`elo_diff`, `is_divisional_game`, `is_international_game`, `travel_km` -- see "Event context" above) -- restricted to columns with at least `MIN_NON_NULL_FRACTION` of the filtered population non-null (a column non-null for only a handful of anomalous rows can still give a shallow tree something irrelevant to exploit even if it isn't literally all-null), and to the target stat's own side of the ball (`OFFENSIVE_CATEGORIES`/`DEFENSIVE_CATEGORIES` in `train_player_prop_model.py`) -- e.g. a passing-yards model never sees `defensive_*` columns at all, regardless of how common they are, since a QB's occasional real (not corrupted) tackle-after-interception stat line is already captured more directly by `avg_passing_interceptions`. Verified against real ESPN data before excluding it -- see the player-prop-passing-yards v3/v4 model cards for the investigation |

Comparing model types is how "best" gets decided rather than assumed, not a one-off analysis: every target's script reads the identical dataset and chronological split for all of its candidates, so their model cards' gate metric (`log_loss` for classification, `rmse` for regression -- the metric that matters for the kind of output being produced, not just accuracy) is directly comparable across algorithms. `library/ml/backtest.py`'s `run_backtest` runs every candidate, writes each one its own versioned artifact and model card (a held-back candidate stays inspectable, never deleted), and calls the existing, algorithm-agnostic `training_common.promote_if_better` on just the winner: a new version is promoted to `model_name`'s "current" pointer unless it's a meaningful regression (see `PROMOTION_TOLERANCE`) against whatever's currently promoted, in which case it's left trained and versioned but not promoted, for manual review. Each winning model card also carries a `candidates` field summarizing every algorithm it beat that run, so the frontend model card view can show what was actually compared.

**Scheduling**: registry-driven, not per-sport hand-cron schedules -- the earlier design (eleven independent `aws_scheduler_schedule` resources, one per training target, staggered 30 minutes apart on Wednesdays to stay under the account's Fargate vCPU quota) was retired once every sport needed the same pattern; see `design/architecture.html`'s pipeline diagram. Today, the monthly `training-orchestrator` Step Function reads NFL's `training_targets` list (still the same eleven: win-probability, one per score target in `nfl_score_targets`, one per player-prop stat in `nfl_player_prop_stats`) off the sport registry and fans them out onto the shared EC2 Spot/on-demand training fleet via a Distributed Map, with concurrency capped by the account's EC2 vCPU budget rather than a hand-picked time-of-day stagger. Which target/stat a given task trains is still set by a `containerOverrides[].environment` override (`SCORE_TARGET`/`TARGET_STAT`) from the registry row, not baked into the task definition itself -- that part of the design didn't change.

## What this makes it possible to predict

**Directly, from these two datasets:**
- **Game outcomes** (win/loss) — trained and evaluated; see the table above.
- **Game scores** — a regressor trained on the same event-level features, predicting `label_home_score` / `label_away_score` (or the margin between them). Not yet built — the dataset and features it would need already exist, no new feature engineering required.
- **Individual player stats** — trained and evaluated; see the table above.

**Not directly — these are simulated, not separately feature-engineered:**
- **Team win-loss totals for a season**, **playoff game winners**, and **Super Bowl winner** are all downstream of the single-game outcome model above, not new feature categories. The standard approach (and the one this project follows): run the game-outcome model's win probability for every remaining game on a team's schedule — or every matchup in a playoff bracket — and simulate forward (e.g. Monte Carlo over those probabilities) rather than training a model whose target *is* "wins this season" or "wins the Super Bowl" directly. There's no separate feature set to build for these; they consume the event-level features and model that already exist here. This logic belongs in a future `predict.py`, not in feature engineering.

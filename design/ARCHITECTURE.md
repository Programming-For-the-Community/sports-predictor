# Architecture

This is the one architecture document for the project — design rationale and as-built reference together, not split across `design/` and `docs/` (they used to be, and drifted out of sync with each other; consolidated here). **For the visual diagrams themselves — client request path, scheduled data pipeline, the in-app AI assistant, observability/cost guardrails — open [`design/architecture.html`](architecture.html) in a browser.** It's a real standalone page (AWS-category-colored, hand-built icons), not a Mermaid render, and it's the single source of truth for those four diagrams; update it alongside this doc whenever the infrastructure changes shape. Everything below is the prose that doesn't fit on a diagram: why each piece exists, the constraints that shaped it, and a plain-text walkthrough of each request/pipeline flow for anyone reading this in a terminal or a Git diff rather than a browser.

All seven sports — NFL, NCAA Football, NBA, NCAA Men's Basketball, NHL, PGA Tour, and F1 — run through the identical architecture described here, registry-driven, differing only in which upstream data source each sport's own adapter calls. Two event shapes underpin everything: **head-to-head** (two teams/competitors — NFL, NCAA FB, NBA, NCAA MBB, NHL) and **field** (many entrants, ranked finish — PGA Tour, F1); see `design/DATA_SCHEMA.md` for how that split shows up in storage.

## Why these specific pieces

Every compute component is either event-triggered (Lambda) or runs only on a schedule and exits (Fargate task, or an EC2 fleet scaled to 0 between runs) — nothing is billed while idle. S3 holds anything large or rarely queried directly (raw pulls, model artifacts); DynamoDB holds anything a Lambda needs to read quickly by key. There's no SageMaker endpoint, no RDS instance — each would add a meaningful fixed monthly cost for a benefit this single-user project doesn't need.

**Predict vs. predict-read vs. live-scores.** Serving splits into three kinds of Lambda, not one, purely for cold-start isolation — `predict` and `live-scores` per sport, `predict-read` shared by every sport:
- **`{sport}-predict`** (container image, ML dependencies) — computes a fresh prediction from current DynamoDB/S3 state and writes an audit-trail row to the predictions table. The only one of the three that's VPC-attached (see "Networking" below).
- **`predict-read`** (zip, no ML dependencies, one Lambda for every sport — `Terraform/lambda-predict-read.tf`) — reads back what each sport's `predict` already wrote (or triggers an async refresh on a stale/missing cache entry). What API Gateway actually invokes for every sport's `/events`, `/models`, `/model-performance`, `/season`, and both `/predictions/...` routes — the hot path every page load hits, so it never pays a cold start for xgboost/scikit-learn/pandas. Not VPC-attached.
- **`{sport}-live-scores`** — cache-only, never writes to the predictions table, kept warm by its own 60-second EventBridge schedule (gated to events near kickoff or in progress) rather than invoked only on a browser request. Not VPC-attached. For football (NFL/NCAAFB) it also keeps ESPN's live `situation` block — which side has the ball, down and distance, field position, red zone — while a play is pending.

**One Flutter codebase, two clients.** The same app ships as the Flutter web build and as an Android APK (arm64, sideloaded — no app store). The APK is built with `--dart-define=ANDROID_APP=true`, which switches on what only the installed app does: a rolling 30-day sign-in, an hourly on-device background job (WorkManager), in-app updates, and home-screen widgets. There's no push service: the background job raises notifications locally — each sport's weekly model report at 10 AM Eastern on its schedule-sync day, and a new-version notice — from the existing API and the published APK's S3 metadata, and refreshes the widgets' data the same way.

**Registry-driven orchestration.** Two scheduled Step Functions state machines, not per-sport EventBridge rules — `ingest-orchestrator` (daily) and `training-orchestrator` (monthly) — each scan a sport registry table and fan out to whichever sports are currently in-season (each row's `season_start`/`season_end` window, checked fresh on every run via a shared `season-gate` Lambda). This replaced an earlier design that gave NFL alone 13 hand-cron EventBridge Scheduler resources — a pattern that would only have gotten more expensive to unwind the more sports copied it, so the refactor was pulled forward ahead of onboarding a second sport rather than done later. Onboarding a new sport today means deploying its own Lambdas/ECS task definitions under the `<project>-<sport>-<stage>` naming convention and adding one registry row — no change to either state machine's own definition. A third state machine, `backfill-orchestrator`, has no schedule: it wraps the manual per-sport backfill (see below).

## Client request path

1. The browser or the Android app sends an HTTPS request to the app's one public domain (Route 53 alias → CloudFront; ACM certs issued in `us-east-1` specifically, since CloudFront requires that regardless of the stack's primary region). CloudFront sits behind a WAF WebACL running AWS's own curated IP-reputation managed rule, and is geo-restricted to a whitelist.
2. CloudFront routes by path: the default behavior (`/*`) serves the Flutter web build from the frontend S3 bucket; `/app/*` serves the Android APK from the mobile-releases bucket, through a CloudFront Function that answers Android user agents only; seven ordered behaviors (`/{sport}/*`, one per sport) forward instead to API Gateway's own custom regional domain — not the raw `execute-api` hostname, which is disabled entirely so no traffic can bypass CloudFront's TLS 1.2 floor.
3. API Gateway validates the request's JWT against the Cognito User Pool via a built-in `COGNITO_USER_POOLS` authorizer — a local signature/claims check against cached JWKS keys, not a network call to Cognito on every request (API Gateway also caches the authorizer result per-token for 5 minutes on top of that).
4. API Gateway invokes the shared `predict-read` for every route except `/{sport}/live-scores`, which goes to that sport's `live-scores` Lambda (see the three-Lambda split above). API Gateway never invokes `predict` itself.
5. `predict-read` answers from the prediction cache in the model-artifacts bucket and the DynamoDB tables: a fresh entry returns 200; a stale one returns 203 with the cached result while it asynchronously invokes the sport's `predict` to refresh it; a missing one returns 202 ("computing") after the same asynchronous invoke, and the app retries. `live-scores` answers from its own S3 cache.
6. `predict` reads live feature history from DynamoDB and the currently-promoted model artifact(s) from S3, scores them, and writes the result to the cache. The prediction scheduler also invokes `predict` directly for the pre-kickoff refresh and snapshot, and on a schedule for season projections.
7. `predict` writes an audit record of each prediction it makes to the predictions table — write-only from its own perspective; `predict-read` is the one that reads that table back, for the predicted-vs-actual comparison on completed events.

## Scheduled data pipeline

**Ingestion**, daily: `ingest-orchestrator` scans the registry, checks each sport's season window via `season-gate`, and invokes that sport's `{sport}-ingest` Lambda by naming convention. Each adapter fetches that day's scoreboard/box scores from its own upstream API and writes raw JSON to the raw-data-lake S3 bucket under a per-sport prefix — nothing else; it never touches DynamoDB directly. Every `PutObject` under a sport's prefix triggers that sport's `{sport}-normalize` Lambda via an S3 event notification, which maps the raw JSON into the shared schema and upserts it into `entities`/`events`/`player_game_stats`/`team_game_stats`. A separate `{sport}-schedule-sync` Lambda per sport, on its own schedule, independently refreshes the *entire* season's calendar (not just the current day).

**One-time historical backfill**: `{sport}-backfill` is a Fargate task per sport that pulls a sport's full multi-year history in one pass. It has no schedule: start it by hand through the `backfill-orchestrator` state machine (`aws stepfunctions start-execution --input '{"sport": "<sport>", "container_overrides": []}'`, see `Terraform/sfn-backfill-orchestrator.tf`), which runs the task with its task-definition tags propagated — a plain `aws ecs run-task` doesn't propagate them. Runs in a public subnet with a public IP — not the private/Gateway-Endpoint path — because it needs to reach its upstream API directly.

**Training**, monthly, once in-season: `training-orchestrator` runs `{sport}-feature-engineering` (Fargate on-demand, reads full history, writes training Parquet to S3), then fans that sport's `training_targets` list out onto a shared **EC2 Spot/on-demand training fleet** (two Auto Scaling Groups, ECS tasks with the `EC2` launch type) via a Distributed Map. This replaced an all-Fargate training path entirely once a real canary run validated EC2 as both cheaper and reliable. Once every sport's map completes, the state machine explicitly scales both ASGs back to 0, waits 20 minutes, then invokes an `ec2-training-reaper` Lambda that terminates any training instance still idle — closing the gap between "desired capacity set to 0" and the ASG actually tearing the instance down. A manually-stopped execution never reaches that far at all, so an EventBridge rule invokes the same Lambda directly off the execution's own ABORTED/FAILED/TIMED_OUT status-change event instead; either way, if something's still not idle, the Lambda self-schedules its own one-time, self-deleting retry a few minutes later, capped at 3 attempts. No recurring schedule triggers it at all — every invocation is caused by something that actually just happened.

## In-app assistant

A chat panel in the app answers questions in plain language. Two agents run on **Amazon Bedrock AgentCore Runtime**, both from one container image (`Source/agents/assistant`); the `ASSISTANT_PROFILE` environment variable picks which one a runtime is:

- **Predictions** (`public`) — everyone signed in. Answers from the app's own predictions, live scores, season projections and model performance only; refuses betting decisions and off-topic requests.
- **Infrastructure** (`admin`) — members of the Cognito `admins` group only. Everything Predictions can do, plus project cost, denied traffic, API traffic, Lambda and pipeline health, training runs and the assistant's own usage.

Infrastructure lives in `Terraform/agentcore-assistant.tf` (runtimes, memory, the assistant table, every tunable as an environment variable), `lambda-assistant-tools.tf`, `lambda-assistant-producers.tf` + `scheduler-assistant-producers.tf`, `bedrock-guardrails-assistant.tf`, `agentcore-evaluations.tf`, `iam-assistant-*.tf`, `cloudwatch-alarms-assistant.tf` and `cloudwatch-dashboard-assistant.tf`. Its resources carry `Component = assistant`.

**Request path.**
1. The panel (`Source/front-end/lib/features/assistant/`) POSTs the question, with the page's sport/event as context, to `/assistant/predictions` or `/assistant/admin` on the app's one domain, carrying the user's Cognito **ID** token, and reads the answer as server-sent events.
2. CloudFront's `/assistant/*` behavior (never cached) runs a CloudFront Function that maps each path to its runtime's invocation URL; any other `/assistant/` path is a 404. The WAF's `assistant-rate-limit` rule caps requests per IP far below the rest of the app, since every question costs model tokens.
3. The runtime's own JWT authorizer checks the token against the user pool and both app clients' audiences; the admin runtime also requires `admins` in `cognito:groups`. There's no API Gateway in this path.
4. The agent runs one turn (`library/assistant/agent_core.py`), streaming `progress` events while tools run, then one `answer` (or `error`) event.

**One turn.** Read the caller's `sub` from the verified token → check the day's quota (per user per Eastern day, 50 public / 300 admin by default) → the agent's Bedrock guardrail on the question → load recent history from AgentCore Memory, the user's saved favourites and answer preferences → the model/tool loop → the guardrail on the answer → write the turn to memory. The loop is capped (4 steps, 10 calls per step, 4 at once, by default). Before an answer goes out, code checks it against the turn: numbers must appear in this turn's tool results, "saved"/"removed" claims need a favourites call, and "let me check" needs an actual call. An answer that fails is sent back to the model once, then replaced with a plain fallback message.

**The model** is whatever `var.assistant_model` names (default Claude Haiku 4.5 via the `us.` cross-region profile; the `ASSISTANT_MODEL` GitHub variable overrides it on deploy). The variable accepts only models from US-based creators. Claude models are called through the Anthropic SDK on Bedrock; others through Bedrock's Converse API (`library/assistant/converse_model.py`). Temperature and effort are variables too.

**Tools.** The model never touches AWS directly: it calls tools, and each tool call is a Lambda invocation from the runtime's role. Tool definitions are built from the sport registry (`library/assistant/tool_specs.py`), so a new sport's registry row adds it to the assistant with no code change.
- **`assistant-public-tools`** — `list_events`, `get_event_prediction`, `get_live_scores`, `get_season_projection`, `get_model_performance`, `get_model_info`, `get_performance_overview`. Reads through each sport's `predict-read` Lambda (the same responses the app shows) and the live-scores S3 cache, then prunes and size-caps the result. Reserved concurrency 20.
- **`assistant-admin-tools`** — `get_cost_summary`, `get_denied_locations`, `get_repeat_offenders`, `get_denied_endpoints`, `get_denied_trend`, `get_api_traffic`, `get_lambda_health`, `get_pipeline_health`, `get_training_runs`, `get_assistant_usage`. Reads the S3 aggregates below, CloudWatch metrics, the events table, the training state machine's executions and the assistant table. Reserved concurrency 5.
- The public agent's role can invoke only the public tool Lambda, so admin tools are out of its reach whatever the model asks for. The favourites and preferences tools (`save_favorite`, `clear_favorites`, `forget_preferences`) run inside the agent itself.

**Background producers.** The admin agent never reads Cost Explorer or raw logs at question time:
- **`assistant-cost-snapshot`**, daily at 14:00 UTC — this project's tagged spend only (the `Project` filter is hard-coded on every Cost Explorer call), by service, sport and component, into `assistant/admin/cost/` in the model-artifacts bucket.
- **`assistant-traffic-aggregate`**, hourly at :10 — Logs Insights counts of blocked/denied requests from both WAF log groups and the API Gateway access log, into `assistant/admin/traffic/`. Request paths are reduced to route templates or sanitised before they're stored, since whoever sends a request writes its path.

**Safety.** Each agent has its own Bedrock guardrail, applied to every question and every answer: content filters, prompt-attack detection on questions, and masking of AWS account ids, ARNs, Cognito user ids and this project's resource names. The public guardrail adds a profanity list, masks IP addresses, and denies two topics: unrelated tasks and infrastructure questions. Betting refusals come from the system prompt, the code checks above and the evaluation judge rather than a guardrail topic, because a topic broad enough to catch betting also blocked ordinary "who's favoured" questions. The admin prompt treats request paths and IP addresses from the traffic tools as untrusted data, never instructions.

**Evaluation.** AgentCore Evaluations scores a sample of sessions (10% by default) with the built-in Faithfulness, Helpfulness and Tool selection accuracy evaluators, plus, on the public agent, a custom LLM judge for staying in scope. The agent emits its own GenAI spans (`library/assistant/gen_ai_spans.py`) for the evaluators to read. An offline case set (`library/assistant/eval_cases.py`, run with `Source/agents/assistant/run_eval.py` inside the agent image) is the check before changing the model or prompts.

**Observability.** Every finished turn writes one JSON line to the runtime's log group (`library/assistant/turn_log.py`): agent, user, session, question, outcome, tools called and the answer. A metric filter turns those lines into the questions/outcomes metrics on the `assistant` dashboard, which also shows the runtimes, Bedrock model tokens, guardrail interventions, the tool and producer Lambdas, Logs Insights views over the turn lines, and evaluation scores. The runtime log groups keep 14 days. Four alarms: turn failures (emails ops-alerts), a spike in guardrail blocks, tool-Lambda errors and producer errors (dashboard only).

**Deploy.** `agents_deploy.yml` (also reached from `app_deploy.yml`) tests, Sonar-scans and builds the arm64 `assistant-agent` image, applies Terraform, points both runtimes at the new image (`agentcore_runtime_deploy.yml`) and deploys the four Lambdas (`assistant_lambdas_deploy.yml`).

## Storage

| Store | Holds |
|---|---|
| S3: Raw Data Lake | Every raw upstream API response, exactly as received, forever, partitioned by sport prefix |
| S3: Model Artifacts | Versioned model binaries, model cards, and training Parquet datasets, partitioned by sport |
| S3: Frontend | The built Flutter web app, served by CloudFront |
| S3: Mobile releases | The Android APK as one object, `app/sports-predictor.apk`, versioned (last 5 builds kept). Its user metadata (`version-code`, `version-name`, `sha256`, `source-hash`, `notes`) is the release signal: the website's Get app button and the app's update check both read it with a HEAD request |
| DynamoDB: entities / events / player_game_stats / team_game_stats | The normalized schema every sport adapter writes to and every serving/training job reads from, partitioned by a `sport` key |
| DynamoDB: predictions | Audit log of every prediction ever served, write-only from each `{sport}-predict`'s perspective |
| DynamoDB: sport_registry | Drives both orchestrators' fan-out — season window, adapter reference, `training_targets` per sport; all 7 sports registered and active. The assistant reads its sport list from here too |
| DynamoDB: assistant | Per user (`pk` = Cognito sub): each day's question count (TTL'd) and saved favourites. Per agent (`pk = usage#<agent>`): daily question counts by outcome, for `get_assistant_usage` |
| AgentCore Memory (one per agent) | Each user's recent conversation turns (kept 7 days, the service minimum) and, through the built-in user-preference strategy, how they've asked to be answered (`/preferences/<sub>`) |
| S3: Model Artifacts, `assistant/admin/` | The cost and denied-traffic aggregates the admin agent reads |

## Networking: no NAT Gateway, anywhere

Only `{sport}-predict` is VPC-attached (private subnets, no public IP) as a defense-in-depth boundary — it's reachable from outside the account, same as `predict-read`/`live-scores`, but it's the one that runs the actual model. `predict-read` and `live-scores` deliberately are **not** VPC-attached: neither ever calls anything but DynamoDB/S3 over the plain AWS API path, so the extra network hop would only add cold-start latency with no real security benefit. The private-subnet comment in `Terraform/subnet-private.tf` spells out why there's **no NAT Gateway** at all — it runs roughly $32/month before any data transfer, a meaningful fixed cost this single-user project doesn't need. `predict` reaches only S3 and DynamoDB, only via VPC Gateway Endpoints (free, no fixed cost) — it has **no route to the public internet at all**, not even a slow or rate-limited one.

This is fine for every route that only ever needs DynamoDB/S3, which is most of them. It becomes a real constraint the moment `predict` needs a live call to an external API — first hit by NCAA MBB's conference-membership resolution (there's no static, low-realignment-risk table for it the way NBA's division table works, and no per-event field for it the way NCAAFB's CFBD source provides one; see `NCAAMBB_FEATURE_ENGINEERING.md`'s "Conference membership" section). The fix, and the general pattern for this constraint going forward:

**S3-relay pattern:** a Lambda that already has ordinary internet egress (ingest, schedule-sync, live-scores — none of these are VPC-attached, since none is `predict`) makes the live call and caches the result to S3 under a scoped prefix; `predict` reads that cache instead of calling out itself. The read still travels over the existing S3 Gateway Endpoint (no security-group or NAT change needed) — the only new grant is a `s3:GetObject` IAM statement scoped to that one prefix (see `iam-lambda-inference.tf`'s `ReadConferenceMembershipCache` statement for the concrete example). Any future sport needing a similar live external lookup from `predict` should reach for this same pattern rather than punching a NAT Gateway hole for one call.

## Access control

The frontend sits at a public URL by design (so it's reachable from anywhere), but every API call requires authentication — there is no anonymous access path.

**Cognito User Pool.** One user pool, self-signup disabled. The project owner creates their own user manually (via the AWS console or CLI) rather than exposing a public registration flow — the only way to obtain a valid token is to already have credentials created that way. Two app clients, both SRP-only sign-in with 1-hour tokens and a 30-day refresh token:
- **`web`** — the website. Refreshes with `REFRESH_TOKEN_AUTH`; the app itself also signs out after 30 minutes without activity.
- **`mobile`** — the Android app. Refresh-token rotation is on (refreshed through `GetTokensFromRefreshToken`, the only path Cognito allows once rotation is on), and the app rotates on every launch and resume, so the 30 days restart each time: the user is only signed out after 30 days away. Rotation needs the Essentials feature plan.

**API Gateway Cognito authorizer.** API Gateway has a built-in integration for validating Cognito-issued JWTs on every request — no custom Lambda authorizer needed. Requests without a valid, unexpired token are rejected at the gateway, before they ever reach a Lambda.

**CloudFront + S3 for the Flutter Web app.** The compiled Flutter app is static and technically loads for anyone who hits the URL, but it's useless without logging in — every data call it makes requires the Cognito token, so an unauthenticated visitor sees a login screen and nothing else.

**The Android APK.** Public under `/app/*` but only to Android user agents (CloudFront Function), and the website only shows its Get app button after sign-in. Like the web build, the APK is useless without a login. Google's developer verification for sideloaded apps applies to it (US enforcement from 2027).

**WAF.** A WebACL in front of CloudFront runs AWS's own curated IP-reputation managed rule, blocking known-malicious IPs before they ever reach an origin — layered on top of, not instead of, the auth requirement above. Its `assistant-rate-limit` rule adds a much lower per-IP cap on `/assistant/*`.

**The assistant.** Its runtimes check the Cognito ID token themselves (AgentCore's JWT authorizer), so `/assistant/*` never passes through API Gateway. Infrastructure mode needs the Cognito `admins` group, checked by the admin runtime's authorizer, not just hidden in the app. Each user also has a daily question quota.

**Usage plan as a further layer.** The API Gateway stage is throttled account-wide (60 requests/second sustained, burst 100) regardless of authentication. Since the project owner is the only legitimate caller, any traffic pattern that would hit this limit is almost certainly not them — a cheap tripwire against scraping or abuse even if a token were ever compromised.

## External dependencies

- Each sport's upstream data API (ESPN, CFBD, Jolpica-F1, etc.) is unofficial/undocumented in most cases — every adapter treats it as a data source only, never assumes a documented contract will hold across seasons.
- **ECR** is pre-existing and shared across projects outside this Terraform stack (referenced via `var.ecr_repo_url`, not managed here) — every container image (each sport's `predict` Lambda, every Fargate feature-engineering/backfill task, the assistant agent) pulls from it.
- **Amazon Bedrock** models for the assistant and its evaluation judge. Which models an account may use is an account-level setting (model access and service quotas), outside Terraform.

## Not shown on `architecture.html`

**IAM roles** — every compute resource runs under its own least-privilege role (`lambda_pipeline` for ingest/normalize/schedule-sync, `lambda_inference` shared by every sport's `predict` and the shared `predict-read`, `lambda_live_scores`, `{sport}_backfill`, `ecs_pipeline`, `stepfunctions_orchestrator`, `eventbridge_invoke`, and for the assistant one runtime role per agent, one role per tool Lambda, the producers' role and the evaluations role) rather than one shared role. `predict-read` reuses `lambda_inference` rather than getting its own scoped-down role — everything it needs (S3 read on model artifacts, DynamoDB read on events/predictions) is already a strict subset of what that role grants `predict`. Not drawn as diagram nodes since IAM is a cross-cutting permissions concern, not a data-flow hop — see the `iam-*.tf` files for the exact policy each role carries.

**Cost controls** (`Terraform/budgets.tf`) — an AWS Budgets alert scoped to this project's cost-allocation tags (project-total and per-sport), emailing at 80%/100% actual spend and 100% forecasted spend. Observes account-wide spend passively rather than participating in any request or data flow, so it isn't drawn either — see `design/TAGGING_STRATEGY.md`.
